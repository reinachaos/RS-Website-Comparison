# RS Website QA implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Work only in the standalone clone and assigned files.

**Goal:** Deliver and upload a repeatable, conservative migration QA suite to the user-provided repository.

**Architecture:** Versioned rules and supplemental catalogs feed bounded browser/network collectors. Pure evaluators and explicit acceptance gates produce escaped evidence reports. Independent offline and browser fixtures test the checker itself.

**Tech Stack:** Node.js 22+, Playwright Test 1.63.0, pixelmatch, pngjs, GitHub Actions.

## Tasks

- [x] Catalog: extract corrected final findings and historical traceability, strip local paths, validate all inventories and rule schemas, and cover empty-anchor and mailto exceptions.
- [x] Evaluator: write failing fixtures, implement pure rules and verify unavailable-source behavior without encoding defects as successful acceptance.
- [x] Report: verify escaping, statuses, partial coverage, safe evidence links and desktop/mobile rendering.
- [x] Collectors: verify bounded read-only HTTP, real browser extraction and interactions, destination restrictions and inert/redacted evidence.
- [x] Runner and baselines: verify selection, exit gates, explicit baseline approval/provenance, primary mappings and complete per-item output after failures.
- [x] Integration: install pinned dependencies, run offline/browser fixtures and full live scope, and inspect generated reports and screenshots. Details are in `docs/verification.md`.
- [x] Delivery preparation: document Chinese/English commands and limitations, add manual live QA and push/PR self-tests, and inspect committed content and upload authentication.

Publication is verified separately through the actual Git push result and matching remote revision, not inferred from this local completion checklist. Only the standalone repository is published; local generated evidence and the original reports remain excluded.

Known site differences may make live QA fail. That is expected and must not be converted into a successful site-acceptance result. An operational test suite and a passing website are different outcomes.
